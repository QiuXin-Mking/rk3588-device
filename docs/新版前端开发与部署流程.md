# 新版前端开发与部署流程

## 1. 部署结构说明

新版界面使用 React、TypeScript 和 Vite 开发，但设备运行时并不是通过 Vite 或 React 开发服务器提供页面。

实际运行结构保持原项目逻辑：

```text
浏览器（设备触摸屏）
        │
        ▼
server.js（Node.js，默认 8080 端口）
        ├── 提供 /api/* 设备接口
        └── 提供 static/ 编译后的前端文件
```

开发源码与运行文件的关系：

```text
frontend/src/         React 和 TypeScript 源码
        │
        │ pnpm build
        ▼
static/               编译后的 HTML、CSS、JavaScript
        │
        │ server.js 读取并提供
        ▼
设备浏览器
```

因此：

- React、TypeScript 和 Vite 只用于开发与构建。
- 设备运行时只需要 Node.js、`server.js`、`package.json`、`config/` 和构建后的 `static/`。
- 不需要在设备上长期运行 `pnpm dev`。
- `server.js` 继续负责原有设备控制和 API，前端构建不会替换后台逻辑。

## 2. 目录职责

| 路径 | 用途 | 是否部署到设备 |
|---|---|---|
| `frontend/src/` | React 前端源码 | 仅设备本机构建时需要 |
| `frontend/index.html` | Vite 开发入口 | 仅构建时需要 |
| `static/` | 生产环境前端文件 | 必须 |
| `server.js` | HTTP 服务、设备 API 和静态文件服务 | 必须 |
| `config/` | 设备运行配置 | 必须保留，部署前端时不要覆盖 |
| `package.json` | ESM 类型及前端构建配置 | 必须保留 |
| `pnpm-lock.yaml` | 锁定前端依赖版本 | 构建时需要 |
| `newdesign/` | 设计参考图 | 运行时不需要 |
| `docs/` | 项目文档 | 可选 |

## 3. 开发环境准备

建议使用：

- Node.js 20 LTS。
- Corepack 管理的 pnpm。
- 与设备相同分支上的最新代码。

首次准备：

```bash
corepack enable
pnpm install --frozen-lockfile
```

依赖只用于开发和构建。当前 `server.js` 本身没有第三方 npm 运行依赖。

## 4. 分支与代码更新

开始开发前先同步目标分支：

```bash
git fetch origin
git switch codex/react-newdesign
git pull --ff-only
```

如果重构分支已经合并到 `main`，则使用：

```bash
git switch main
git pull --ff-only
```

不要直接在设备的生产目录内进行未经验证的界面修改。

## 5. 本地开发

启动 Vite 开发服务器：

```bash
pnpm dev --host 127.0.0.1
```

默认访问地址：

```text
http://127.0.0.1:5173/
```

当前 Vite 配置没有开发环境 API 代理，因此本地开发服务器主要用于界面和离线状态检查。前端请求使用相对路径 `/api/*`，完整设备联调应通过生产构建后的 `server.js` 进行。

开发过程中至少检查：

- 1920×1080 横屏。
- 1080×1920 竖屏兼容模式。
- 中文和英文。
- 浅色和深色主题。
- 长名称、大量列表和弹窗。
- 页面根节点无整体滚动。
- 浏览器控制台无错误。

## 6. 构建生产版本

执行：

```bash
pnpm build
```

构建过程包含：

1. TypeScript 类型检查。
2. Vite 生产构建。
3. 清空旧的 `static/` 构建内容。
4. 生成新的 `static/index.html` 和带内容哈希的资源文件。

成功后主要文件类似：

```text
static/
├── index.html
└── assets/
    ├── index-xxxxxxxx.css
    └── index-xxxxxxxx.js
```

构建后必须检查：

```bash
git diff --check
```

还应确认：

- `server.js` 没有因为纯前端发布被意外修改。
- `config/` 没有被构建过程修改。
- `static/index.html` 引用的 CSS 和 JavaScript 文件实际存在。

## 7. 本机生产方式验证

在开发机进行基础验证：

```bash
PORT=8080 RECORD_DIR=/media/usb0/capture node server.js
```

打开：

```text
http://127.0.0.1:8080/
```

开发机缺少设备服务、摄像头、挂载目录或 systemd 服务时，部分 API 失败属于正常现象；重点检查页面是否能加载、导航是否可用、离线状态是否正确显示。

验证完成后停止测试进程，避免与其他实例争用 8080 端口。

## 8. 推荐部署方式：开发机构建，设备只接收产物

这是推荐方式。设备不需要安装完整前端依赖，部署时间短，也更容易回滚。

### 8.1 在开发机生成发布包

```bash
pnpm install --frozen-lockfile
pnpm build
tar -czf sensorhub-static.tar.gz static
```

发布包只包含编译后的 `static/`。

### 8.2 上传到设备临时目录

示例：

```bash
scp sensorhub-static.tar.gz root@设备IP:/tmp/
```

### 8.3 确认设备项目目录和服务方式

仓库中没有包含确定的 systemd unit 文件，因此部署前必须先在设备上确认：

- 实际项目目录。
- `server.js` 是手工启动、启动脚本启动，还是 systemd 管理。
- 如果是 systemd，实际服务名称是什么。

以下示例假设项目目录是 `/opt/device-ui`，实际部署时必须替换：

```bash
APP_DIR=/opt/device-ui
```

不要猜测服务名称，也不要修改与前端发布无关的设备服务。

### 8.4 解压并备份当前版本

```bash
APP_DIR=/opt/device-ui
RELEASE_ID=$(date +%Y%m%d-%H%M%S)
DEPLOY_DIR=$(mktemp -d /tmp/sensorhub-static.XXXXXX)

tar -xzf /tmp/sensorhub-static.tar.gz -C "$DEPLOY_DIR"
mkdir -p "$APP_DIR/backups"
cp -a "$APP_DIR/static" "$APP_DIR/backups/static-$RELEASE_ID"
```

确认临时目录包含：

```bash
test -f "$DEPLOY_DIR/static/index.html"
test -d "$DEPLOY_DIR/static/assets"
```

### 8.5 停止 Web 服务并替换静态目录

如果由 systemd 管理：

```bash
systemctl stop <实际服务名>
mv "$APP_DIR/static" "$APP_DIR/static.replaced-$RELEASE_ID"
mv "$DEPLOY_DIR/static" "$APP_DIR/static"
systemctl start <实际服务名>
```

如果是手工启动，则先正常停止原来的 `node server.js` 进程，替换 `static/` 后按照原启动方式重新启动。

此步骤只替换 `static/`，不要覆盖：

- `server.js`
- `config/`
- 录制目录
- 校准配置
- systemd 配置

## 9. 可选部署方式：设备上拉代码并构建

RK3588 设备具有 8 GB 内存，可以在设备上构建，但生产发布更推荐使用上一节的构建产物方式。

设备本机构建流程：

```bash
cd <设备项目目录>
git fetch origin
git switch <目标分支>
git pull --ff-only
corepack enable
pnpm install --frozen-lockfile
pnpm build
```

构建成功后，按照设备原有方式重启 `server.js`。

注意：

- `pnpm build` 会重建并清空旧 `static/` 内容。
- 构建前应备份当前 `static/`。
- 不要在录制任务进行中更新。
- 不要同时运行多个 `server.js` 实例。

## 10. 服务启动参数

当前后台支持的主要环境变量：

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `PORT` | `8080` | Web UI 和 API 端口 |
| `RECORD_DIR` | `/media/usb0/capture` | 录制目录 |
| `CAL_PORT` | `8888` | 校准器服务端口 |
| `SPP_ADDR_LEFT` | 后台内置地址 | 左手蓝牙手套地址 |
| `SPP_ADDR_RIGHT` | 后台内置地址 | 右手蓝牙手套地址 |
| `GLOVE_PID_LEFT` | `5739` | 左手有线手套 PID |
| `GLOVE_PID_RIGHT` | `5740` | 右手有线手套 PID |
| `STEREO_CTL_SOCK` | `/tmp/stereo_ctl.sock` | 双目相机控制 socket |

手工启动示例：

```bash
PORT=8080 RECORD_DIR=/media/usb0/capture node server.js
```

生产环境应沿用设备当前已有的启动参数，不应仅因为更新前端而改变这些值。

## 11. 部署后验证

### 11.1 服务检查

```bash
curl -f http://127.0.0.1:8080/
curl -f http://127.0.0.1:8080/api/status
curl -f http://127.0.0.1:8080/api/record/status
```

如果使用 systemd：

```bash
systemctl status <实际服务名>
journalctl -u <实际服务名> -n 100 --no-pager
```

### 11.2 页面检查

- 页面可以正常打开。
- 顶部标题、返回按钮和底部导航正常。
- 浅色、深色、中文和英文切换正常。
- 页面没有整体滚动或横向溢出。
- 设备离线时页面不会白屏。

### 11.3 原功能冒烟测试

- `/api/status` 能显示设备状态。
- 相机实时预览可以启停。
- 录制可以开始和停止。
- 记录列表可以打开。
- 记录预览、解码、传输和删除入口正常。
- Wi-Fi 可以扫描、连接和断开。
- 蓝牙可以扫描、连接和断开。
- 左右手套校准流程可以进入和返回。
- 设置可以读取并保存。

没有后台支持的占位功能只需要确认位置和“待接入”提示正常，不能把提示出现当成接口成功。

## 12. 回滚流程

发现严重问题时优先回滚 `static/`，不修改后台和设备配置。

```bash
APP_DIR=/opt/device-ui

systemctl stop <实际服务名>
mv "$APP_DIR/static" "$APP_DIR/static.failed"
cp -a "$APP_DIR/backups/<需要恢复的备份目录>" "$APP_DIR/static"
systemctl start <实际服务名>
```

回滚后重新执行：

```bash
curl -f http://127.0.0.1:8080/
curl -f http://127.0.0.1:8080/api/status
```

确认恢复成功后，再单独保存或清理失败版本。不要删除唯一可用备份。
